1. Core issue: FAQ schema
The problem: FAQPage schema cannot be added through the site's content editor. Per the client's report, when the schema is added via the editor it renders as visible code in the page body instead of valid JSON-LD. Our scan of all 220 pages confirms the outcome and locates a live example: no page on the site carries a valid FAQPage, and on one page, /polygraph-concerns-and-how-to-handle-them/, a broken FAQ attempt is present.

The live example (the only page with a FAQ attempt): the JSON itself is valid and contains 5 questions, but it fails for two reasons: it is declared as type="application/json" instead of application/ld+json (Google ignores it entirely), and it sits inside a <p> tag in the body content. This is exactly what the client reported.

<!-- What currently exists on /polygraph-concerns-and-how-to-handle-them/ -->
<p>
  <script id="data" type="application/json">
  {
    "@context": "https://schema.org",
    "@type": "FAQPage",
    "mainEntity": [ { "@type": "Question", "name": "איך נראה מבחן אמינות?", ... } ]
  }
  </script>
</p>

Root cause (what actually happens)

The technical issue: the site is built on a custom theme (midot-th), with no page builder on the content pages. When the content team pastes <script type="application/ld+json"> code into the WordPress content field, WordPress treats it as untrusted editor content: the sanitization layer (wp_kses) strips the <script> tag on save (for users without the unfiltered_html capability), or TinyMCE converts it to entities. What remains, the JSON body, is printed by the theme as visible text on the page. This is not a one-off glitch but a structural mismatch: schema code cannot live inside an editor content field.

Why it cannot be fixed through the editor: the unfiltered_html capability must not be granted (stored-XSS risk), switching between editor modes re-encodes the code, and maintaining visible text plus separate JSON in parallel drifts over time. On top of that, a manual <script> creates a second graph that conflicts with Yoast's graph. The fix must be at the template/code level, not in the editor.

The correct fix (for the dev team)

  1. Structured fields: add a repeating question+answer field group (ACF repeater: faq_items[question, answer]) to the product and post content types. The content editor fills in a question and an answer, not code.
  2. One source, dual render: the theme PHP renders both the visible text and the JSON-LD from the same fields, so the visible content and the schema are always identical (a Google requirement).
  3. Integrate into Yoast's graph: add the FAQPage via the wpseo_schema_graph filter. Extend the existing WebPage node (add the FAQPage type to it) and add Question nodes with acceptedAnswer, instead of injecting a second <script>. This avoids a duplicate/conflicting graph.
  4. Only when content exists: emit a FAQPage only when at least one complete question+answer pair exists. An empty field produces no schema.
  5. Where to put the code: place the schema logic in a small functionality plugin rather than the theme itself, so it survives a theme swap/update.

Note: the attempt on the polygraph page survived as a script tag with the wrong type (application/json). Other attempts may be re-encoded as visible text (as the client reported). Both cases share the same root cause: schema code cannot be added correctly through the editor.

A valid JSON-LD structure (real example from the IntegriTEST page):

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "isPartOf": { "@id": "https://midot.co.il/product/integritest/" },
  "mainEntity": [
    {
      "@type": "Question",
      "name": "מהו מבחן אמינות ממוחשב IntegriTEST ומה הוא בודק?",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "מבחן IntegriTEST של מכון מידות הוא כלי אבחון ממוחשב, שנועד להעריך את רמת היושרה והאמינות של מועמדים לעבודה. המבחן מתמקד בזיהוי נטיות להתנהגויות בלתי רצויות במקום העבודה, כגון גניבה, הונאה, שימוש בסמים ואלכוהול, ושוחד."
      }
    },
    {
      "@type": "Question",
      "name": "מהי המטרה של מבחן אמינות ממוחשב?",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "המטרה המרכזית היא לספק למעסיקים כלי מדעי ומדויק להערכת הסבירות שמועמד יפגין התנהגויות בלתי הולמות במקום העבודה, ובכך לסייע בקבלת החלטות מושכלות בתהליך הגיוס."
      }
    }
  ]
}
</script>
Setting expectations: Google narrowed FAQ rich results to government and health sites only, and Midot is neither. So the value of FAQPage here is not a rich result in Google but a machine-readable Q&A structure that helps search engines and AI engines understand the content (the AI-engine value is a working assumption, not a guaranteed outcome). It is also the foundation that will let the content team add Q&A correctly from now on.

3. Inconsistent Product schema on product pages

Of 13 product pages, 10 carry Product schema, but 2 are missing it entirely. An inconsistency in the WooCommerce product template.

Product with no Product schemaURL
Computerized integrity test (IntegriTEST)/product/integritest/
Frontal reliability interview/product/ראיון-מהימנות-פרונטאלי/

What to do: ensure the product template emits Product for all products uniformly. Base structure:

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "מבחן אמינות ממוחשב (IntegriTEST)",
  "description": "כלי אבחון ממוחשב להערכת יושרה ואמינות של מועמדים לעבודה.",
  "brand": { "@type": "Brand", "name": "מכון מידות" },
  "url": "https://midot.co.il/product/integritest/"
}
</script>
Use only real fields. Do not invent price, availability, sku or aggregateRating. If there is no real price/rating, simply omit the field. Note: without a real offers or aggregateRating, Product will not earn a rich product result in Google, but it still tells engines this is a product and strengthens entity recognition.
4. Acceptance tests for the developer

To confirm the fix works correctly:

  • Adding a Q&A row renders a readable question+answer and valid JSON-LD.
  • Removing all rows removes the FAQPage block entirely.
  • A partial row (question without an answer) produces no schema.
  • HTML inside an answer is safely encoded (without breaking the JSON).
  • A single page has no duplicate FAQPage / Product / Organization / WebPage.
  • Validate each page in Google's Rich Results Test after rendering, not just the template snippet.

Below this line: background and considerations. Not required for implementation.

Detection method

The site uses Google Tag Manager and JavaScript, so some schemas do not appear in the source HTML the server returns. All findings were verified against the rendered DOM in a real browser (Headless Chrome), exactly the way Google sees the page. Product and blog pages were checked against the rendered DOM (including a re-check of slow-loading pages). In addition, all 220 content pages were scanned in the source with several instruments: valid FAQPage (ld+json), broken FAQPage (wrong script type), and schema code leaked as text. It was the multi-instrument check that located the broken attempt on the polygraph page. For every recommendation, we confirmed in the browser that the schema is genuinely absent on the target page, to avoid duplication.
