1. בעיית הליבה: סכמת FAQ
הבעיה: לא ניתן להוסיף סכמת FAQPage דרך עורך התוכן של האתר. לפי דיווח הלקוח, כאשר מנסים להוסיף את הסכמה דרך העורך, היא מוצגת כקוד גלוי בגוף העמוד במקום כ-JSON-LD תקין. הבדיקה שלנו על כל 220 העמודים מאשרת את התוצאה ואף מאתרת דוגמה חיה: אין באתר אף FAQPage תקין, ובעמוד אחד, /polygraph-concerns-and-how-to-handle-them/, נמצא ניסיון FAQ שבור.

הדוגמה החיה (העמוד היחיד עם ניסיון FAQ): ה-JSON עצמו תקין וכולל 5 שאלות, אך הוא נכשל משתי סיבות: הוא מוגדר כ-type="application/json" במקום application/ld+json (גוגל מתעלמת ממנו לחלוטין), והוא יושב בתוך תגית <p> בגוף התוכן. זה בדיוק מה שהלקוח דיווח עליו.

<!-- מה שקיים היום בעמוד /polygraph-concerns-and-how-to-handle-them/ -->
<p>
  <script id="data" type="application/json">
  {
    "@context": "https://schema.org",
    "@type": "FAQPage",
    "mainEntity": [ { "@type": "Question", "name": "איך נראה מבחן אמינות?", ... } ]
  }
  </script>
</p>

סיבת השורש (מה באמת קורה)

הבעיה הטכנית: האתר בנוי על תבנית ייעודית (midot-th), ללא Page Builder בעמודי התוכן. כשצוות התוכן מדביק קוד <script type="application/ld+json"> לתוך שדה התוכן של וורדפרס, וורדפרס מתייחס אליו כתוכן עריכה לא מהימן: מנגנון הסינון (wp_kses) מסיר את תגית ה-<script> בעת השמירה (למשתמשים ללא הרשאת unfiltered_html), או ש-TinyMCE ממיר אותה לישויות. מה שנשאר, גוף ה-JSON, מודפס על ידי התבנית כטקסט גלוי בעמוד. זו אינה תקלה נקודתית אלא אי-התאמה מבנית: קוד סכמה לא יכול לחיות בשדה תוכן עריכה.

למה אי אפשר לתקן דרך העורך: אין להעניק הרשאת unfiltered_html (סיכון XSS מאוחסן), מעבר בין מצבי עריכה מקודד את הקוד מחדש, ותחזוקה כפולה של טקסט גלוי + JSON נפרד מתפצלת עם הזמן. בנוסף, <script> ידני יוצר גרף שני שמתנגש עם הגרף של Yoast. הפתרון חייב להיות ברמת התבנית/הקוד, לא בעורך.

הפתרון הנכון (למחלקת הפיתוח)

  1. שדות מובנים: להוסיף קבוצת שדות שאלה+תשובה חוזרים (ACF repeater: faq_items[question, answer]) לסוגי התוכן product ו-post. עורך התוכן ממלא שאלה ותשובה, לא קוד.
  2. רינדור כפול ממקור אחד: קוד ה-PHP של התבנית מרנדר מאותם שדות גם את הטקסט הגלוי וגם את ה-JSON-LD, כך שהתוכן הנראה והסכמה תמיד זהים (דרישת גוגל).
  3. שילוב בגרף של Yoast: להוסיף את ה-FAQPage דרך הפילטר wpseo_schema_graph. להרחיב את צומת ה-WebPage הקיים (להוסיף לו את הסוג FAQPage) ולהוסיף צמתי Question עם acceptedAnswer, במקום להזריק <script> שני. כך נמנע גרף כפול/מתנגש.
  4. רק כשיש תוכן: להפיק FAQPage רק כאשר קיים לפחות זוג שאלה+תשובה מלא. שדה ריק לא מפיק סכמה.
  5. מיקום הקוד: מומלץ למקם את לוגיקת הסכמה בתוסף פונקציונליות קטן ולא בתבנית עצמה, כדי שתשרוד החלפת/עדכון תבנית.

הערה: הניסיון בעמוד הפוליגרף שרד כתגית script עם סוג שגוי (application/json). ניסיונות אחרים עשויים להתקודד כטקסט גלוי (כפי שהלקוח דיווח). שני המקרים הם אותה סיבת שורש: קוד סכמה לא יכול להתווסף נכון דרך העורך.

מבנה JSON-LD תקין (דוגמה אמיתית מעמוד IntegriTEST):

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "isPartOf": { "@id": "https://midot.co.il/product/integritest/" },
  "mainEntity": [
    {
      "@type": "Question",
      "name": "מהו מבחן אמינות ממוחשב IntegriTEST ומה הוא בודק?",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "מבחן IntegriTEST של מכון מידות הוא כלי אבחון ממוחשב, שנועד להעריך את רמת היושרה והאמינות של מועמדים לעבודה. המבחן מתמקד בזיהוי נטיות להתנהגויות בלתי רצויות במקום העבודה, כגון גניבה, הונאה, שימוש בסמים ואלכוהול, ושוחד."
      }
    },
    {
      "@type": "Question",
      "name": "מהי המטרה של מבחן אמינות ממוחשב?",
      "acceptedAnswer": {
        "@type": "Answer",
        "text": "המטרה המרכזית היא לספק למעסיקים כלי מדעי ומדויק להערכת הסבירות שמועמד יפגין התנהגויות בלתי הולמות במקום העבודה, ובכך לסייע בקבלת החלטות מושכלות בתהליך הגיוס."
      }
    }
  ]
}
</script>
תיאום ציפיות: גוגל צמצמה את תצוגות ה-FAQ המועשרות לאתרי ממשל ובריאות בלבד, ומידות אינה כזו. לכן הערך של FAQPage כאן אינו תוצאה מועשרת בגוגל, אלא מבנה שאלות-תשובות קריא-מכונה שמסייע להבנת התוכן על ידי מנועי חיפוש ומנועי AI (הערך במנועי AI הוא הנחת עבודה, לא תוצאה מובטחת). זו גם התשתית שתאפשר לצוות התוכן להוסיף שו"ת בצורה תקינה מעכשיו והלאה.

3. סכמת Product לא עקבית בעמודי המוצר

מתוך 13 עמודי מוצר, ב-10 קיימת סכמת Product, אך ב-2 מהם היא חסרה לחלוטין. חוסר עקביות בתבנית המוצר של WooCommerce.

מוצר ללא סכמת Productכתובת
מבחן אמינות ממוחשב (IntegriTEST)/product/integritest/
ראיון מהימנות פרונטאלי/product/ראיון-מהימנות-פרונטאלי/

מה לעשות: לוודא שתבנית המוצר מפיקה Product לכל המוצרים באופן אחיד. מבנה בסיסי:

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "מבחן אמינות ממוחשב (IntegriTEST)",
  "description": "כלי אבחון ממוחשב להערכת יושרה ואמינות של מועמדים לעבודה.",
  "brand": { "@type": "Brand", "name": "מכון מידות" },
  "url": "https://midot.co.il/product/integritest/"
}
</script>
להשתמש רק בשדות אמיתיים. אין להמציא price, availability, sku או aggregateRating. אם אין מחיר/דירוג אמיתי, פשוט להשמיט את השדה. שימו לב: ללא offers או aggregateRating אמיתיים, Product לא יזכה לתצוגת מוצר מועשרת בגוגל, אך עדיין מבהיר למנועים שמדובר במוצר ומחזק את זיהוי הישות.
4. בדיקות קבלה למפתח

כדי לאשר שהפתרון עובד נכון:

  • הוספת שורת שו"ת מרנדרת שאלה+תשובה קריאים וגם JSON-LD תקין.
  • הסרת כל השורות מסירה את בלוק ה-FAQPage לחלוטין.
  • שורה חלקית (שאלה ללא תשובה) לא מפיקה סכמה.
  • HTML בתוך תשובה מקודד בבטחה (ללא שבירת ה-JSON).
  • בעמוד בודד אין כפילות של FAQPage / Product / Organization / WebPage.
  • לאמת כל עמוד ב-Rich Results Test של גוגל לאחר הרינדור, לא רק את קטע התבנית.

מכאן ומטה: רקע ושיקולים. לא נדרש להטמעה.

שיטת הבדיקה

האתר משתמש ב-Google Tag Manager וב-JavaScript, ולכן חלק מהסכמות אינן מופיעות בקוד המקור שהשרת מחזיר. כל הממצאים אומתו על ה-DOM המרונדר בדפדפן אמיתי (Headless Chrome), בדיוק כפי שגוגל רואה את העמוד. עמודי המוצר והבלוג נבדקו על ה-DOM המרונדר (כולל אימות חוזר של עמודים שנטענו לאט). בנוסף, כל 220 עמודי התוכן נסרקו בקוד המקור, במספר מכשירים: FAQPage תקין (ld+json), FAQPage שבור (סוג script שגוי), וקוד סכמה שדלף כטקסט. הבדיקה במספר מכשירים היא שאיתרה את הניסיון השבור בעמוד הפוליגרף. לכל המלצה אומת בדפדפן שהסכמה באמת חסרה בעמוד היעד, כדי למנוע כפילות.
