01A 404 page is publishing a person's detailsdev · three lines

/leadership/atul-malik/ returns HTTP 404 and still outputs a Person entity for Atul Malik, with his job title and a url pointing at /leadership/hartesh-juneja/. A page that does not exist is currently asserting that a named individual does.

WhereThe wpseo_schema_graph filter in qmd-schema.php.
Why it happensThe file registers /leadership/atul-malik/ as well as the current slug, so the markup would survive the planned rename. The rename has not been done, so that path is a 404, and the filter has no 404 guard.
ScopeOne page. Nothing else is affected.
FixThree lines, below.
Confirm it workedLoad /leadership/atul-malik/, view source. There should be no Person node, and no @type beyond Yoast's own.
add_filter( 'wpseo_schema_graph', function ( $graph ) {

	if ( is_404() ) {            // <-- add these three lines
		return $graph;
	}

	$path  = qmd_schema_path();
	$nodes = qmd_schema_nodes();

	if ( ! empty( $nodes[ $path ] ) ) {
		foreach ( $nodes[ $path ] as $node ) {
			$graph[] = $node;
		}
	}
	return $graph;
} );

Renaming the slug to /leadership/atul-malik/ with a 301, as originally intended, also resolves it, because the path stops being a 404. The guard is worth adding either way: it stops any future path in the map from leaking a node onto a missing page.

Verified two ways: headless Chrome and a plain curl both return 404 with the Person node present in the body.

02The twelve leadership profiles are set to noindexneeds a decision

ProfilePage and Person are correctly implemented on all twelve profile pages, and they validate cleanly. They cannot earn anything, because all twelve carry <meta name='robots' content='noindex, follow'> and Google will not index them.

What carries itSixteen URLs: the twelve leadership profiles, plus /leadership/, /leadership/page/2/, /product/ and /product-category/coronary-products/.
Effect on the markupNone of the ProfilePage work can produce a result while this stands. The markup is correct; the pages are excluded.
Who decidesQMD. This is a question about whether those pages belong in the index, not a schema question.
Verified byThe raw HTML, the rendered DOM, and Google Search Console, which reports these URLs as excluded by a noindex tag.

Two ways forward.

  • If the profiles should be indexed: remove the noindex on the leadership post type. Nothing in the schema changes, and the pages return to the index over the following weeks.
  • If the noindex is deliberate: the twelve Person nodes are doing nothing where they are. Move them onto /qmd-leadership/, which is indexable, ranks, and already lists all twelve with their titles and photographs.

Their absence from the sitemap and their missing canonical tags both follow automatically from the noindex. Neither is a separate fault.

Working as intended · do not "fix" these

Two things that will look like faults and are not

The product pages will report as ineligible. Once Google recrawls them, the Rich Results Test and Search Console may list the fourteen product pages as invalid under Product snippets, because they carry no price, review or rating. That is the expected result of a quote-based catalogue and it was the accepted trade-off. Do not add a price, a currency, an availability value or a rating to clear it. That single change is the only thing that would turn accurate markup into a false claim.

The homepage no longer reports a Breadcrumbs rich result. That is the intended outcome. Its breadcrumb contained a single item, and Google requires at least two, so it could never have qualified. Removing it cost nothing. Every inner page keeps its full trail.
