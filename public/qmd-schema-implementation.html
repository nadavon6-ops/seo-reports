02BreadcrumbListalready live · 1 fix

Breadcrumbs already work on this site. Yoast outputs a correct four-level trail on product pages, for example Home › Products › Arthesys™ Products › PTCA Catheters. Do not add breadcrumb markup, and do not touch the inner pages: duplicating it would be worse than leaving it alone.

There is exactly one defect. On the homepage the trail contains a single item, Home, and Google's requirement is to define a BreadcrumbList that contains at least two ListItems. A one-item trail cannot qualify, so it is removed on the homepage only.

ScopeOne fix, homepage only.
Appears onEvery page already. Only https://qmd.net/ changes.
Repeat per pageNo. Yoast already generates the trail dynamically per page.
Already on the siteYes, and correct everywhere except the homepage.
How it is implementedIn the file in section 09: the wpseo_schema_needs_breadcrumb filter, plus two lines inside the single wpseo_schema_webpage callback that section 05 also uses. There is one such callback in the file, not two.
Google resultInner pages already carry valid breadcrumb markup, which is what makes them eligible. This fix removes an invalid trail; it does not change inner pages.
Confirm it workedThe homepage source contains no BreadcrumbList and no leftover breadcrumb reference, while a product page still shows its four-level trail.

Both halves are required. Yoast attaches the breadcrumb reference to the WebPage node unconditionally, skipping it only on a 404. Removing the piece without also removing the reference would leave the homepage pointing at an @id that no longer exists.

// 1. stop Yoast emitting the one-item breadcrumb on the homepage
add_filter( 'wpseo_schema_needs_breadcrumb', function ( $needed ) {
	return ( '/' === qmd_schema_path() ) ? false : $needed;
} );

// 2. remove the reference that would otherwise point at the deleted node
//    (inside the wpseo_schema_webpage filter)
if ( '/' === $path ) {
	unset( $data['breadcrumb'] );
}

Read this before running the Rich Results Test. These blocks carry no offers, no review and no aggregateRating, because QMD publishes no prices, no reviews and no ratings. Google's rule is explicit: Product snippets require either review or aggregateRating or offers. So the Rich Results Test will report the product item as ineligible and Search Console may list these pages as invalid under Product snippets. That is the expected outcome, not a defect. Do not add a zero price, a placeholder currency, an availability value or an invented rating to clear it. That would state something false about a quote-based business.

What the markup is for here is entity understanding: it states that QMD manufactures these devices and which of the three acquired brands each belongs to. For a contract manufacturer, that relationship is the commercial proposition, and no other schema type expresses it.

05Page types

Three pages are typed as a generic WebPage when a more specific type applies. This adds no node, it refines the one already there, so the @id and every existing relationship stay intact.

ScopeThree specific pages.
Appears on/about/, /contact/, /qmd-leadership/.
Repeat per pageNo. One mapping covers all three.
Already on the siteThe WebPage node exists; only its @type changes.
How it is implementedIn the file in section 09, in the same single wpseo_schema_webpage callback used by section 02.
Google resultNone. These are descriptive types, not SERP features.
Confirm it workedThose three pages report the new @type; every other page still reports WebPage.
add_filter( 'wpseo_schema_webpage', function ( $data ) {
	$path = qmd_schema_path();
	$types = array(
		'/about/'           => 'AboutPage',
		'/contact/'         => 'ContactPage',
		'/qmd-leadership/'  => 'CollectionPage',
	);
	if ( isset( $types[ $path ] ) ) {
		$data['@type'] = $types[ $path ];
	}
	return $data;
} );

function qmd_schema_path() {
	$uri  = isset( $_SERVER['REQUEST_URI'] ) ? wp_unslash( $_SERVER['REQUEST_URI'] ) : '/';
	$path = wp_parse_url( $uri, PHP_URL_PATH );
	if ( ! $path ) {
		$path = '/';
	}
	return trailingslashit( $path );

/**
 * 1. Enrich the Organization node Yoast already owns.
 *    The @id, url, logo and image are left exactly as Yoast emits them, so every
 *    existing reference in the graph keeps resolving.
 */
add_filter( 'wpseo_schema_organization', function ( $data ) {
	return array_merge( $data, qmd_schema_organization_data() );
} );

/**
 * 2. Refine the WebPage @type and attach mainEntity where the page is genuinely
 *    an about page, a contact page, a person profile or a collection.
 */
add_filter( 'wpseo_schema_webpage', function ( $data ) {
	$path  = qmd_schema_path();
	$types = qmd_schema_page_types();
	$mains = qmd_schema_main_entities();

	if ( isset( $types[ $path ] ) ) {
		$data['@type'] = $types[ $path ];
	}
	if ( isset( $mains[ $path ] ) ) {
		$data['mainEntity'] = array( '@id' => $mains[ $path ] );
	}

	// The homepage Breadcrumb piece is removed below. Yoast's WebPage generator adds the
	// 'breadcrumb' reference unconditionally (it only skips it on a 404), so the reference
	// has to be removed here too or the homepage would point at an @id that no longer exists.
	if ( '/' === $path ) {
		unset( $data['breadcrumb'] );
	}

	return $data;
} );

/**
 * 3. Append the Person, ItemList, Product and OfferCatalog nodes to the graph.
 *    Nothing is printed separately -- these become part of Yoast's single @graph.
 */
add_filter( 'wpseo_schema_graph', function ( $graph ) {
	$path  = qmd_schema_path();
	$nodes = qmd_schema_nodes();

	if ( ! empty( $nodes[ $path ] ) ) {
		foreach ( $nodes[ $path ] as $node ) {
			$graph[] = $node;
		}
	}
	return $graph;
} );

11Two fixes outside the schema

Neither is markup, but both affect what the markup describes.

  • A profile URL carries the wrong name. /leadership/hartesh-juneja/ is Atul Malik's page. Change the slug to /leadership/atul-malik/ with a 301 from the old path.
    If you do the rename, the schema needs two edits. The file matches pages by request path, and a 301 does not make the new path match the old key. The file already registers both paths, so the markup keeps working the moment the slug changes. What it does not do automatically is update the person's own identifiers: change "url" and "@id" on that Person node, and the matching entry in the leadership ItemList, from hartesh-juneja to atul-malik. Three values, one find and replace.
  • Sixteen live URLs are in no sitemap. The sitemap index lists only page-sitemap.xml and product-sitemap.xml. All sixteen return 200, are indexable and draw search traffic. They split into two different fixes:
    • Thirteen are a settings change. In Yoast, Search Appearance › Content Types, set the leadership post type to show in search results, which adds the twelve profiles. In Search Appearance › Taxonomies, do the same for the product category taxonomy, which adds /product-category/coronary-products/.
    • Three are a decision, not a setting. /leadership/, /leadership/page/2/ and /product/ are archive and pagination URLs. Yoast's content-type settings do not add them. Decide whether each should be indexed and included, or noindexed and left out. They currently sit in between: indexable but undiscoverable from the sitemap.
