Midot: Schema Status — Outstanding Items

A re-audit of the full site against the original schema report. This document lists only what still needs to be implemented; everything already working correctly has been deliberately left out.

Site: midot.co.il Re-audited: August 2026 URLs crawled: 226 Method: Rendered DOM

Can the task be closed?

Not yet — four implementation items remain. They are listed below, in the order we would tackle them.

Substantial progress since the original report. The FAQ mechanism has been built and is now emitting valid FAQPage JSON-LD on 13 blog pages, all of which we re-validated in the rendered DOM for this document. At the time of the original report, not a single page on the site carried a valid FAQPage. One of the two missing Product implementations has also been completed.

What remains is narrow and specific. The FAQ mechanism was applied to the post content type but not to product, so product pages that display a real question-and-answer section still emit no schema for it. Alongside that, one legacy broken block and one missing Product node are still live.

1 Extend the FAQ mechanism to product pages

Three product pages display a full, visible question-and-answer section to users, but emit no FAQPage. The content is already written and on the page — only the schema output is missing.

What to do

Register the same question/answer field group already in use on post against the product content type, and have the product template emit the FAQPage node from those fields exactly as the blog template does. This is an extension of the mechanism that already works, not a new build.

Emit the node only when a complete question and answer pair exists, so a half-filled row produces no schema. The questions in the schema must match the questions visible on the page word for word.

3 Remove the legacy broken FAQ block

One page still carries the original broken attempt described in the previous report. It is unchanged.

Page: /polygraph-concerns-and-how-to-handle-them/

The block holds five valid questions, but it is declared as type="application/json" instead of type="application/ld+json", and it sits inside a <p> tag in the body content. Google ignores it completely, so this page is currently getting no benefit from Q&A content that is already written.

<!-- currently live on the page -->
<p>
  <script id="data" type="application/json">
    { "@context": "https://schema.org", "@type": "FAQPage",
      "mainEntity": [ { "@type": "Question", "name": "איך נראה מבחן אמינות?", ... } ] }
  </script>
</p>

What to do

  1. Move the five existing questions and answers into the working FAQ field group for this page.
  2. Delete the <script id="data"> block from the body content.
Do not simply change the MIME type in place. That would leave a second, separately maintained copy of the Q&A in the body content, which drifts out of sync with the visible text over time — the problem the field-based mechanism was built to solve.
4 Add the missing Product schema

Twelve of the thirteen product pages now emit Product. One does not.

Page: /product/integritest/

This is the only remaining gap in the product template’s coverage.

<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "מבחן אמינות ממוחשב (IntegriTEST)",
  "description": "כלי אבחון ממוחשב להערכת יושרה ואמינות של מועמדים לעבודה.",
  "brand": { "@type": "Brand", "name": "מכון מידות" },
  "url": "https://midot.co.il/product/integritest/"
}
</script>
Use real fields only. Do not add price, availability, sku or aggregateRating unless the values are genuine — omit the field instead.

6 Acceptance tests before closing the task

The task can be closed once all four items above are deployed and the following hold true:

  1. Adding a question and answer pair renders readable text and valid JSON-LD, on both the post and product types.
  2. Removing all pairs removes the FAQPage block entirely.
  3. A partial pair (question with no answer) produces no schema.
  4. HTML inside an answer is safely encoded and does not break the JSON.
  5. No page carries a duplicate FAQPage, Product, Organization or WebPage node.
  6. No application/json schema block remains anywhere in body content.
  7. Each affected URL passes Google’s Rich Results Test after rendering, not as a template snippet.
A note on expectations, unchanged from the original report: Google restricts FAQ rich results to government and health sites, so the value here is a machine-readable Q&A structure for search and AI engines, not a visual rich result in Google.
7 How this was verified

Every finding above was confirmed against the rendered DOM in a real browser — the way Google sees the pages. Raw HTML was pulled separately and diffed against the rendered result: the two agree on this site, so its schema is server-rendered rather than injected by JavaScript. The rendered DOM remains the instrument of record, because it is what Google evaluates and it is the only way to confirm the full graph as assembled on the page.

  • 226 URLs enumerated from all eleven sitemaps and rendered in headless Chrome.
  • 167 URLs returned HTTP 200 and were parsed for every application/ld+json block, including arrays and @graph structures.
  • Each page was also checked for visible question-and-answer content, so that no schema is recommended where the content does not support it.
  • Nothing is recommended here without first confirming in the rendered DOM that it is genuinely absent. Duplicate schema is worse than none.
