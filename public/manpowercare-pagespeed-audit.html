Lazy Load פועל על תמונת ה‑LCP — התמונה הראשית בראש העמוד נטענת באיחור

קריטי
עמודים מושפעים
https://manpowercare.co.il/מטפלת-סיעודית/ — LCP 10.2s
https://manpowercare.co.il/טיפול-בנכי-צהל/ — LCP 8.9s
https://manpowercare.co.il/מחשבון-גמלת-סיעוד/ — LCP 8.1s
https://manpowercare.co.il/החשיבות-של-מטפלת-סיעודית/ — LCP 6.0s
מה נכשל

מדד Largest Contentful Paint — 6.0 עד 10.2 שניות במקום 2.5. שימו לב לפער: ה‑FCP (רגע הצגת התוכן הראשון) הוא 2.9–3.2 שניות בלבד — כלומר העמוד מתחיל להיראות מהר, אבל התמונה הראשית מגיעה 5–7 שניות אחר כך.

למה זה קורה

ה‑Lazy Load של WP Rocket מוחל גם על התמונה הראשית שבראש העמוד. בקוד רואים את זה במפורש — Elementor סימן את התמונה כדחופה, ו‑WP Rocket דרס את זה:

<img fetchpriority="high" ... src="data:image/svg+xml,..." data-lazy-src="https://manpowercare.co.il/.../atar6-1-1-1024x571.webp">

ה‑src האמיתי הוחלף ב‑placeholder ריק, והכתובת האמיתית הועברה ל‑data-lazy-src. התוצאה: הדפדפן לא יכול להתחיל להוריד את התמונה עד שה‑JavaScript של Rocket ירוץ — וזה קורה רק אחרי שכל ה‑CSS וה‑JS החוסמים סיימו. זה הגורם מספר 1 לציון המובייל הנמוך.

מה לעשות
  1. ב‑WP Rocket → Media → תחת LazyLoad, בשדה "Excluded images or iframes" להוסיף את התמונות שבראש כל תבנית עמוד (ה‑hero). אפשר להוסיף לפי מחרוזת בנתיב, למשל: atar6-1-1, pinmobile, /uploads/2026/07/.
  2. לחלופין ועדיף כפתרון גורף — WP Rocket מציע "Excluded first images" / הגדרת דילוג על N התמונות הראשונות. להגדיר ל‑2.
  3. לוודא אחרי התיקון שהתמונה הראשית מגיעה ב‑HTML עם src אמיתי + fetchpriority="high" וללא data-lazy-src.
השפעה צפויה: הורדת LCP במובייל ב‑4–6 שניות. לבדו — קפיצה של כ‑20–25 נקודות בציון.

וידאו אוטומטי של 2.2MB בראש דף הבית — הוא זה שנמדד כ‑LCP

קריטי
עמוד מושפע
https://manpowercare.co.il/ — LCP 9.0s · משקל עמוד 3,112KB
מה נכשל

LCP 9.0s · Total byte weight 3,112KB · Main-thread work 4.4s. דף הבית שוקל פי 2–3 מכל שאר העמודים באתר.

למה זה קורה

בראש דף הבית יש שני אלמנטי <video> עם autoplay, כולל קובץ אחד במשקל 2,226KB (WhatsApp-Video-2026-05-07-...mp4). זהו קובץ שהועלה ישירות מוואטסאפ ללא דחיסה או אופטימיזציה לווב. הווידאו לבדו הוא 72% ממשקל העמוד כולו, ו‑Lighthouse מזהה אותו כאלמנט ה‑LCP — כלומר Google מודד את הציון של דף הבית לפי כמה זמן לוקח לווידאו הזה להתחיל לרוץ. בנוסף אין לו מאפיין preload, כך שהדפדפן מוריד אותו במלואו במקום את המטא‑דאטה בלבד.

מה לעשות
  1. במובייל — להחליף את הווידאו בתמונת poster סטטית. ב‑Elementor להגדיר את סקשן הווידאו כמוסתר במובייל, ובמקומו סקשן תמונה עם hero-poster.webp (32KB בלבד, כבר קיים בשרת). זה הפתרון המהיר והמשמעותי ביותר.
  2. לדחוס מחדש את קובץ ה‑MP4: H.264, רזולוציה 1280px, ~1.5Mbps — היעד הוא מתחת ל‑500KB במקום 2.2MB.
  3. להוסיף preload="none" ו‑poster="hero-poster.webp" לתגית הווידאו, כך שהדפדפן יציג מיד תמונה ויתחיל להוריד את הווידאו רק אחרי הטעינה.
  4. לשקול העברת הווידאו מתחת לקיפול (below the fold) — כך הוא מפסיק להיות אלמנט ה‑LCP לחלוטין.
השפעה צפויה: הורדת משקל דף הבית מ‑3.1MB ל‑כ‑900KB, ו‑LCP מ‑9.0s ל‑כ‑2.5s.

31–39 קבצי CSS ו‑22–42 קבצי JS נפרדים — אופטימיזציית WP Rocket כבויה

קריטי
עמודים מושפעים
כל 6 העמודים שנבדקו (36 קבצי CSS בדף הבית, 39 ב"מטפלת סיעודית", 37 ב"סניפים")
מה נכשל

Eliminate render-blocking resources — חיסכון מוערך של 1,240–1,520ms בכל אחד מהעמודים. זה המדד הכי עקבי בכל האתר.

למה זה קורה

WP Rocket מותקן ופעיל, אבל רק ה‑DNS Prefetch דלוק — פיצול/איחוד CSS, טעינת CSS אסינכרונית ו‑Delay JavaScript כבויים. התוצאה: הדפדפן חייב להוריד ולעבד עשרות קבצים לפני שהוא מצייר משהו. הקבצים החוסמים המובילים:

jquery.min.js — 468ms (נטען בראש העמוד, חוסם)
jquery-migrate.min.js — 156ms (ספריית תאימות ישנה)
30+ קבצי elementor/css/post-*.css ו‑widget-*.css — 156ms כל אחד
jet-search.css, jet-tabs-frontend.css, easybility/style.css
מה לעשות
  1. WP Rocket → File Optimization → להפעיל Minify CSS + Optimize CSS delivery → Remove Unused CSS (זו ההגדרה שפותרת את רוב הבעיה — Rocket מייצר Critical CSS inline ודוחה את השאר).
  2. להפעיל Minify JavaScript + Load JavaScript deferred.
  3. להפעיל Delay JavaScript execution, ולוודא שהחרגות כוללות את הסקריפטים של ה‑hero בלבד.
  4. לבדוק אם jquery-migrate באמת נחוץ — ברוב אתרי Elementor המודרניים אפשר להסיר אותו (יש תוסף ייעודי או שורת wp_deregister_script ב‑functions.php).
  5. חשוב: אחרי הפעלת Remove Unused CSS לעבור על העמודים המרכזיים ולוודא שאין שבירות עיצוב — במיוחד ב‑RTL, בתפריט המגה‑מניו ובקרוסלות.
השפעה צפויה: הורדת 1.2–1.5 שניות מזמן הטעינה בכל עמוד באתר.

סקריפט ה‑Cookie Banner (OneTrust) חוסם את הרינדור למשך 1.35 שניות

גבוה
עמודים מושפעים
כל האתר — 163KB מ‑cdn.cookielaw.org בכל עמוד
מה נכשל

Render-blocking resources: הקובץ OtAutoBlock.js לבדו מבזבז 1,354ms. בנוסף: Use preconnect — חיסכון של 310–440ms.

למה זה קורה

OneTrust נטען כסקריפט חוסם בראש ה‑<head>, מדומיין חיצוני (cdn.cookielaw.org) שלא הוגדר לו preconnect — רק dns-prefetch, שחוסך פחות. הדפדפן צריך לפתוח חיבור TLS חדש לדומיין זר לפני שהוא ממשיך לצייר את העמוד. סה"כ OneTrust מביא 163KB ומעסיק את ה‑main thread ב‑133–139ms.

מה לעשות
  1. להוסיף ל‑<head>, לפני הסקריפט:
    <link rel="preconnect" href="https://cdn.cookielaw.org" crossorigin>
    <link rel="preconnect" href="https://geolocation.onetrust.com" crossorigin>
  2. להעביר את otSDKStub.js ל‑async (במקום סקריפט חוסם), ולוודא שהוא נטען אחרי ה‑CSS הקריטי.
  3. לבדוק אם OtAutoBlock.js באמת נדרש — הוא נועד לחסימה אוטומטית של קוקיז צד‑שלישי. אם הטראקינג ממילא מנוהל דרך Consent Mode ב‑GTM, אפשר להסיר אותו ולחסוך את מלוא ה‑1.35 שניות.
  4. להוסיף את OneTrust לרשימת ה‑Delay JavaScript של WP Rocket (עם בדיקה שהבאנר עדיין עולה תקין).
השפעה צפויה: 0.5–1.3 שניות בכל עמוד באתר.

גופן Noto Sans Hebrew נטען מ‑Google Fonts כקובץ חוסם, ללא font-display

גבוה
עמודים מושפעים
כל האתר — https://fonts.googleapis.com/earlyaccess/notosanshebrew.css
מה נכשל

Render-blocking resources: קובץ ה‑CSS של הגופן מבזבז 1,594ms. Ensure text remains visible during webfont load: שני קבצי WOFF2 חוסמים הצגת טקסט למשך 1,781ms ו‑1,478ms.

למה זה קורה

שלוש בעיות בו‑זמנית: (א) הגופן נטען מדומיין חיצוני — הדפדפן צריך שני חיבורים נפרדים (fonts.googleapis.com ואז fonts.gstatic.com) לפני שהטקסט מוצג; (ב) נעשה שימוש ב‑endpoint earlyaccess, גרסה ישנה שאינה כוללת font-display: swap; (ג) אין preconnect לדומייני הגופנים. התוצאה — הטקסט בעברית פשוט לא מוצג במשך כמעט 1.8 שניות.

מה לעשות
  1. הפתרון הטוב ביותר — לארח את הגופן מקומית. להוריד את Noto Sans Hebrew בפורמט WOFF2 (משקלים 400 ו‑700 בלבד), להעלות ל‑/wp-content/themes/hello-theme-child-master/fonts/ ולהגדיר @font-face עם font-display: swap. מבטל שני חיבורים חיצוניים.
  2. להוסיף <link rel="preload" as="font" type="font/woff2" crossorigin> לקובץ הגופן הראשי.
  3. אם נשארים ב‑Google Fonts — לפחות לעבור מ‑earlyaccess ל‑endpoint הרגיל עם &display=swap, ולהוסיף preconnect ל‑fonts.gstatic.com.
  4. WP Rocket → Preload → להפעיל Preload Fonts.
השפעה צפויה: 0.8–1.5 שניות, ושיפור מיידי בחוויית המשתמש — הטקסט מופיע מיד.

תמונות כבדות שלא עברו אופטימיזציה + הפניית 301 בכל כתובת באתר

הפניות — כל כתובות האתר

Avoid multiple page redirects — חיסכון של 600–930ms במובייל. כל כתובת ללא סלאש בסוף מקבלת 301:

https://manpowercare.co.il/branches → 301 → https://manpowercare.co.il/branches/

המשמעות: כל משתמש שמגיע מגוגל או מקישור פנימי משלם סיבוב רשת נוסף לפני שהעמוד בכלל מתחיל להיטען.

מה לעשות
  1. להעלות מחדש את pinmobile.webp ברוחב מקסימלי של 800px ולהריץ עליו ShortPixel במצב Glossy — היעד: מתחת ל‑80KB.
  2. ב‑ShortPixel להפעיל Resize large images ל‑1920px, ולהריץ Bulk Optimize על כל ספריית המדיה כדי לתפוס קבצים דומים שהועלו בגדלים מקוריים.
  3. לוודא שכל תמונה בתוכן יוצאת עם srcset מלא — כרגע רק חלק מהתמונות כוללות אותו.
  4. לתקן את הקישורים הפנימיים כך שיצביעו ישירות לכתובת עם סלאש בסוף (/branches/), ולוודא שה‑Sitemap וה‑canonical מכילים את הגרסה עם הסלאש.
השפעה צפויה: 0.6–0.9 שניות מההפניות, ועוד כ‑1.5 שניות בעמוד "מטפלת סיעודית" מהתמונה.
